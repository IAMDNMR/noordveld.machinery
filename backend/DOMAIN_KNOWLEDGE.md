# Domain knowledge foundation

Shared, versioned business knowledge that Design Studio projects reuse: domains, concepts, entities, attributes,
relationships, events, rules, processes, open decisions and source-system mappings. Code: `app/domain_knowledge/`,
routes: `app/api/routes/domain_knowledge.py` (`/api/v1/domain-knowledge`), UI: `/design-studio/domains` and the
"Shared domain knowledge" panel on the business designer's Knowledge tab.

## Layers

| Layer | Model (`models.py`) | Notes |
|---|---|---|
| A. Domain registry | `Domain` | Parent/subdomain and `depends_on` graphs must be acyclic. |
| B. Ontology | `Concept`, `Synonym` | Synonyms hold within a named domain. Equivalence is explicit, never inferred from similar names. A concept is distinct from the entity that represents it. |
| C. Entities and attributes | `Entity`, `Attribute` | Type, key/unique, value source, mutability, sensitivity, code list. System-managed values cannot be user-updated. |
| D. Relationships | `Relationship` | Source, type, target, cardinality, meaning, required, acyclic flag, provenance. Endpoints must be entities or concepts. Duplicates and prohibited cycles are rejected. |
| E. Behaviour | `Event`, `Rule`, `Process`, `Decision` | Processes point at Design Studio workflow templates. Decisions stay `open` until the business owner answers them. |
| F. Source mappings | `SourceMapping` | Source system/entity/attribute to canonical attribute, with transform and code translation. |

Every item carries `Provenance`: `verified_source`, `derived`, `synthetic`, `user_provided` or `assumption`, plus a
verification state. Assumptions and synthetic items cannot be marked verified, and an assumption rule cannot be confirmed.

## Authoritative stores

| Data | Authoritative store | Identifier | Updates |
|---|---|---|---|
| Shipped domain packs | `app/domain_knowledge/packs/*.json` (versioned files) | `pack_id` + semver | Regenerated by `scripts/build_domain_pack.py`; byte-identical for identical sources. |
| Proposed, approved and deprecated versions, plus the audit trail | `DomainStore`: `ReadOnlyDomainStore` (default, deployed) or `SqliteDomainStore` (isolated local app only) | `(pack_id, version)` | Insert-only versions; lifecycle transitions are audited. |
| Project-specific copies and overrides | The Design Studio project revision (`business.entities[*].origin`) | `dk_<entity id>` | Saved with the project's normal revision check; never written back to the pack. |
| Graph representation | Neo4j `DK*` namespace | `dk_key = pack_id\|version\|item_id` | **Not populated.** A dry-run plan only (see below). |

There is no distributed transaction and no synchronisation job. Files and the domain store are the source of truth,
and the graph would be a derived, idempotent projection of an approved version.

## Lifecycle and governance

`draft → under_review → approved → deprecated` (and `under_review → draft`). Approving takes another person than the
proposer, and the only approved version of a pack cannot be deprecated. A version's content never changes; a change
is a new version. Imports run as a dry run first: validation, normalization log, diff against the active version,
semver compatibility (breaking changes need a major bump) and judgement findings (possible duplicates, ambiguous
terms). Applying requires the dry run's content fingerprint and a reason, and only creates a proposal. Re-importing
identical content is idempotent. The active version (latest approved) is what discovery and the explorer use. Existing
projects keep their copies, and a newer version shows up as `KNOWLEDGE_STALE`. Nothing is rewritten.

### Permissions (enforced by the server)

| Action | Permission |
|---|---|
| Propose a version (import apply), resubmit a draft | `domain.propose` |
| Return a proposal to draft | `domain.review` |
| Approve a version (never your own) | `domain.approve` |
| Deprecate a version (never the last approved one) | `domain.administer` |

Permissions come from the `get_domain_access` dependency (`app/domain_knowledge/store.py`). The trusted identity
model cannot distinguish domain administrators yet, so by default **nobody** holds a domain permission, and the
default store is read-only anyway. The isolated local app grants them explicitly: Alice holds propose and review; Bob
holds all four. The UI greys out buttons the user lacks, but the server is what refuses. Wiring real assignments is
an integration step for the approved identity provider.

When approving, the server re-checks the version: it must have no blocking validation findings and must be a
compatible semantic-version step from the active version. Otherwise the response is 409 and the version stays
under review.

## Design Studio integration

`POST /suggest` matches the description against domain keywords, concept names and in-domain synonyms. It returns
matched concepts with provenance, ambiguous terms, required dependencies, reusable processes and open decisions, and
copies nothing. `POST /adopt` copies only the selected entities, plus relationships between selected entities. Missing
required targets are reported, not added. Each copy records its origin. `POST /overrides` lists adopted entities that
differ from the shared definition. The `/impact/{item}` endpoint lists pack items that depend on an item, plus the
caller's project entities, steps and screens copied from it.

## Multi-hop intelligence

`traversal.KnowledgeGraph` answers bounded, explained queries. It is breadth-first, has an explicit depth (1–6) and
result limit (1–200), and keeps one shortest path per node, so cycles cannot loop. Every result carries the hops that
reach it, each with a sentence explaining why it holds. `pack_graph(pack)` covers domains, concepts, entities,
attributes, relationships, events, rules, processes, roles, decisions and mappings (`GET /domain-knowledge/traverse`).
`compiler.project_graph` covers a project: requirements → steps → operations/screens → generated files, plus adopted
domain items → project entities (`GET /design-studio/projects/{id}/dependencies`). The graphs are built in memory from
the authoritative pack or project revision. They are small enough that no index is needed, and nothing reads Neo4j.

## Domain-to-application compiler (`app/design_studio/compiler.py`)

`approved packs + project revision → resolve → specify → plan → generate → check`, each stage typed (pydantic):

- **resolve** (`DomainResolution`): the pack versions the project's adopted entities came from and their status. It
  reports overrides, unresolved required dependencies (errors; never added for you), mixed versions of one pack
  (error), unapproved versions (error), newer active versions (info) and open decisions affecting adopted items.
- **specify** (`ApplicationSpecification`): turns relationships into behaviour. A to-one relationship becomes a
  reference. That is the declared foreign-key attribute when the source has one named like the target's key;
  otherwise it is a link field named after the relationship, supplied on create. Required relationships are validated
  on create, to-many relationships become collection views, and every step that reads or writes an entity becomes an
  operation with its permission and the roles that hold it.
- **plan** (`GenerationPlan`): each file, its kind and its sources. It is blocked while there are resolution errors,
  blocking design findings or no valid design approval for the current revision.
- **generate**: the existing artifact generator plus `src/generated/relationships.ts` with its test,
  `design/forms.json`, `relationships.json`, `operations.json`, `domain-provenance.json` and `specification.json`.
  It also adds link fields to the OpenAPI input schemas and writes `generation-manifest.json`, which records file
  ownership and digests plus the project revision, pack versions and compiler/generator versions.
- **check**: static checks: JSON parses, OpenAPI `$ref`s resolve, reference targets have schemas, writes name
  permissions held by roles, digests match, every file is traced. Generated code is not executed by the server. The
  test suite compiles the TypeScript and runs both generated test files in an isolated workspace.

The archive (`GET …/compile/archive`) is served only when compilation is not blocked and no check fails.
`POST …/compile/update-plan` tells a workspace how to apply a new generation safely. It replaces only files unchanged
since generation, keeps and reports files a person edited, and never touches files the generator does not own.
Compilation is read-only and deterministic: identical inputs give byte-identical files. A proposal or newly approved
pack version does not change a project's output; the project compiles from the versions it adopted until someone
re-adopts, which is a normal edit that makes the previous approval stale.

| Artifact | Kind |
|---|---|
| `src/generated/*.ts` (models, validation, relationships) and their tests | Executable source |
| `design/forms.json`, `relationships.json`, `operations.json` | Validated configuration |
| `schemas/*.schema.json`, `api/openapi.json` | Contract (no implementation) |
| `src/App.tsx` mockup | Preview only |
| `design/*` other, `manifest.json`, `generation-manifest.json` | Manifest |
| Backend implementation, database migrations, integration adapters, access enforcement | Unsupported (listed in `design/artifacts.json`) |

## Neo4j: proposed, not executed

The namespace (`DKDomain`, `DKConcept`, `DKEntity`, `DKAttribute`, … and `DK_*` relationship types) is checked
against `graph/schema/*.csv` and has no collisions with operational labels or types. `graph.py` provides:

- `SCHEMA_PROPOSAL`: unique constraints on `dk_key` per label and two indexes. **Requires operation-specific authorization.**
- `write_plan(pack)`: parameterized, idempotent `UNWIND … MERGE` statements to load one pack version. **Requires authorization.**
- `READ_QUERIES`: parameterized read-only Cypher for the explorer's questions.

`GraphDomainProvider` is disabled. No configuration enables it, and `apply_schema` / `apply_write_plan` always raise
`WriteNotAuthorized`. To proceed, the owner must authorize, separately: (1) the constraint/index statements,
(2) loading a named pack version via its write plan, and (3) wiring a read-only session for `READ_QUERIES`.

## Releases of `noordveld_machinery`

| Release | Content |
|---|---|
| 1.0.0 | Frozen history, still shipped and approved. 45 entities, 84 relationships. |
| 1.1.0 (active) | Additive: adds **transport management (TMS)** and **warehouse operations (WMS)** on the same model. 55 entities, 102 relationships, 12 domains, application roles, 4 more open decisions. Passes the validation report with no blocking findings; the 1.0.0→1.1.0 comparison is classified `additive`. |

**TMS/WMS content.** Grounded in the repository: `route` and `route_leg` (from `data/canonical/logistics`; attribute types come
from the values present, and `distance_km`, empty in every source row, stays `string` / `needs_review`), and 22 tracking-event
transitions copied from `app/logistics/rules.py` (`verified_source`). Everything the sources do not define is an **unverified
assumption**, never a fact: `transport_request`, `transport_plan`, `vehicle`, `proof_of_delivery`, `transport_exception`,
`pick_task`, `pack_unit`, `fulfilment_handoff`, five rules, and five application roles. The relationships connect the chain
order line → pick task → pack unit → fulfilment handoff → transport request → transport plan → shipment → tracking events →
proof of delivery. Warehouse operations and transport meet at the handoff (`rel_fulfilment_handoff_hands_off_to_transport_request`).

**Explicit domain dependencies.** `Domain.dependencies` states `required`, `optional` or `conditional` (with its condition) per
dependency. TMS requires logistics, core and commerce, and *conditionally* depends on warehouse operations ("goods are collected
from a managed warehouse"). Warehouse operations requires inventory and commerce and treats procurement as optional. The 1.0.0
dependencies were never classified by the business, so they are `unclassified`, not "required".

**Application roles** (`app_roles`) belong to one application (`tms` or `wms`). They are not organization roles; users hold them
through explicit per-application grants (see `ORGANIZATIONS.md`).

**Design Studio reference pack** `noordveld_transport` (built by `scripts/build_transport_reference_pack.py` from the domain pack):
two workflows (31 steps): `wf_transport_lifecycle` (request → plan → eligibility → assign → capacity → goods ready → dispatch →
tracking → delivery outcome → proof of delivery, with exception paths for no carrier, over capacity, goods not released, delayed
or failed delivery, missing proof; ends delivered or cancelled) and `wf_warehouse_fulfilment` (stock check → allocate → pick →
pack → completeness → handoff). Stock availability and allocation rules are copied verbatim, with their source, from the existing
order flow; every other rule introduced is an assumption, the four new business decisions stay open, and the carrier tracking feed
is a deferred integration. A project created from it is blocked from approval only by those open decisions until each is decided
or deferred with a reason.

## Assistant and voice providers

`app/assistant/` holds the typed contracts (a `ChangeProposal`, a `TranscriptSubmission` that is shown to the user first and is idempotent, and the
`AssistantProvider` / `SpeechProvider` protocols) and the Design Studio conversation built on them: typed actions applied by a deterministic engine, a language
model or labelled local rules as planner, and Deepgram speech. Speech is on when `DEEPGRAM_API_KEY` is present (off with `STUDIO_VOICE=off`); the language model is
`AI_PROVIDER` / `LLM_PROVIDER` (off with `STUDIO_ASSISTANT=off`). `GET /design-studio/voice/status` and `GET /assistant/status` report what is enabled and why;
credentials are never read back or returned (only whether a variable exists). See `docs/STUDIO_VOICE_FIRST_2026_10_15.md`.

## Neo4j environment

The repository has one graph connection (`NEO4J_*`): the live operational graph. No separate development instance is
configured, so **no domain-graph write is possible or attempted**. `GET /domain-knowledge/graph-provider` reports an `isolation`
block (names only, never values) with the blocker; a dedicated instance with its own credentials (proposed `DOMAIN_GRAPH_URI`) is
a prerequisite for any write, and separate labels inside the operational graph do not count as isolation.

## Noordveld Machinery pack: how 1.0.0 was built

Built from `graph/schema/node_schema.csv`, `relationship_schema.csv` and `identifier_contract.md`, the lifecycle and
inventory CSV headers in `data/canonical/`, and the rules, decisions and workflows of the Design Studio pack
`noordveld_spare_parts`. Contents: 10 domains, 45 entities, 84 relationships, 46 concepts, plus events, rules, 2
process templates, 8 open decisions and identifier mappings. Graph `SOURCE_DERIVED` items become `verified_source`.
`DERIVED` items become `derived` / `needs_review`, and `SYNTHETIC_DEMO` items become `synthetic`. Domain
classification and the curated synonyms are editorial and marked `derived` / `needs_review`. Attribute types are
established from the values the source actually contains (`graph/cypher/*.cypher` seed rows and canonical CSVs). An
attribute without observed values stays `string`, marked `needs_review`.
